# 工作方法

本项目的要求：**用最少的代码把功能做完整，并且不出错**。本文件规定动手前怎么想、写多少、哪些代码不许写。目录职责与命名见 [DEVELOPMENT](DEVELOPMENT.md)，授权边界见 [AGENTS](../../AGENTS.md)。每次开发都按本文件执行，不得以“更稳妥”为由偏离。

**本文件是对其他文档的补充。** 与 [AGENTS](../../AGENTS.md)、[DEVELOPMENT](DEVELOPMENT.md)、[DESIGN](DESIGN.md)、[DECISIONS](DECISIONS.md) 冲突时，以那些文档为准；本文件不新增产品或结构决定，发现冲突时报告给用户修订本文件。

最重要的五条：

1. 先读要改的代码和它的调用方（引用它的组件、页面），再动手。
2. 只做本任务需要的改动，不顺手重构、不改无关文件。
3. 先复用已有代码，其次 HeroUI 组件与浏览器 / React 自带能力，再其次已有依赖，最后才写新代码。
4. 不写为“万一”准备的判空、校验、兜底和 `try`/`catch`。
5. 代码放进 DEVELOPMENT 目录职责表中对应的位置，不新建杂物目录。

## 一、开发步骤

1. 读 [NOW](NOW.md) 确认任务；读 DEVELOPMENT、DESIGN 中与任务相关的章节，改结构或选型前查 DECISIONS。
2. 读要改的代码和所有引用方，按下一节的清单想清楚影响面。
3. 实现：按第三、四节的要求写最少的代码；界面先查 HeroUI 有没有现成组件。
4. 核心逻辑按第五节判断是否写测试。
5. 按第八节自查，执行 `npm run check`。
6. 按 [AGENTS 的完成标准](../../AGENTS.md#完成标准) 更新文档，写交付报告。提交、推送、删除文件、增删依赖须先经用户同意。

## 二、动手前：先想清楚影响面

先读要改的代码和引用它的代码，再逐项过一遍下面的清单。清单的目的是**找出必须处理的情况**，不是给每种情况都加代码：大多数项的答案是“不受影响”。

| 检查项       | 要回答的问题                                                                          |
| ------------ | ------------------------------------------------------------------------------------- |
| 引用方       | 这个组件、props、类型、样式类还有谁在用？改了谁会坏？                                 |
| 已保存的数据 | 用户浏览器里已有的 `localStorage`、URL 参数、书签还能用吗？（未发版前不做旧数据兼容） |
| 状态与时序   | 加载中、空数据、请求失败、快速连点、组件卸载后请求才返回，各是什么表现？              |
| 外部输入     | 数据来自网络接口、URL、用户输入吗？在读入处校验一次即可                               |
| 完整流程     | 用户做完这一步，下一步看到的东西对吗？列表要不要刷新、按钮要不要立即进入加载态？      |
| 屏幕与主题   | 窄屏、宽屏、深色模式、减少动效（`prefers-reduced-motion`）下是否正常？                |
| 可访问性     | 能否用键盘操作、焦点可见、图标按钮有无 `aria-label`？（用 HeroUI 组件大多已满足）     |

想清楚之后：

- 只有会改变产品行为的问题（新功能、默认值、要不要询问用户、是否删除用户数据）才**先问用户**，可以给出带理由的建议，不自行决定。技术细节按已有代码的写法自己决定，不拿来问用户。
- 用户报告问题时，**先实测找到原因再改**，不凭猜测同时改几处。
- 修缺陷改**根因所在的共用代码**一次，不在每个调用处各打补丁；界面问题要排查全项目同类写法。

## 三、写多少：最少的代码

按顺序选第一个能完整解决问题的方案：

1. **能不能不写？** 没人要求的选项、配置、扩展点不做。只在交付报告里一句话说明“未做什么”。
2. **项目里已经有吗？** 先找再写，复用已有组件与函数。
3. **HeroUI 或平台自带吗？** 按钮、输入、弹层、下拉、提示等用 HeroUI；格式化用 `Intl`，请求用 `fetch`，状态先用 React 自带的 `useState` / `useReducer` / Context。
4. **已有依赖能做吗？** 不为几行代码加依赖；确需新依赖时说明用途并经用户同意。
5. 以上都不行，才写新代码，写能工作的最少代码。

具体要求：

- 不写“以后可能用到”的代码：只有一处使用的抽象、只转发一次的包装组件、没人传的 props、只有一个实现的接口或工厂。
- 能一行看懂的就一行；但需要反复推敲才懂的一行不算短，拆开写。
- 注释只写代码看不出的**原因**，一行为宜；不复述代码在做什么。
- **有意的简化必须留 `shortcut:` 注释**，写清限制和何时升级，例：`// shortcut: 列表一次性渲染，超过 500 条再改虚拟滚动。`
- 删除优于新增：功能被替代后，在交付说明中列出要删的旧组件、样式与文案，**经用户同意后**一起删干净。
- 不越界：不顺手重构、不重新格式化无关文件、不改名、不“顺便”修别处；看到其他问题写进交付报告，由用户决定。

## 四、不许写的防御性代码

下面这些**一律不写**：

- **对类型已保证存在的值判空或写可选链。** TypeScript 类型就是契约，类型说必有就直接用；真可能缺失时把类型写成可选，在一处处理。
- **对内部 props、参数重复校验。** 校验只在边界做一次：用户输入（表单提交）、网络响应与 URL 参数（读入时）。
- **为“不可能发生”的状态写分支或兜底值。** 真的发生说明有缺陷，应当暴露出来。
- **用 `any`、`as` 断言或 `@ts-ignore` 绕过类型错误。** 修类型本身；外部数据在读入处收窄一次。
- **自造重试、超时、降级包装。** 确有需要时在请求层统一做一处。
- **“以防万一”的 `try`/`catch`**，规则见下一节。

### `try`/`catch` 什么时候写

只在下面几种情况写，每处都要能说出它防住了什么：

| 情况                   | 做法                                                                             |
| ---------------------- | -------------------------------------------------------------------------------- |
| 外部数据解析           | 在读入处**集中捕获一次**，转为带说明的错误或界面提示；不在每个字段读取处各自捕获 |
| 可有可无的数据         | 如 `localStorage` 中的偏好读不出时用默认值，界面照常运行                         |
| 能给用户有用提示的失败 | 请求失败时按原因显示对应提示（网络断开、无权限、未找到）                         |
| 必须撤销的操作         | 乐观更新失败后回滚界面状态                                                       |

以下写法**禁止**：

- 捕获后什么都不做，或只 `console.log` 后继续。
- 在每个组件里各包一层 `try`/`catch`；渲染错误交给错误边界（首次需要时在 `src/app/` 建立）。
- 在调用方再包一层已经由被调用方处理过的错误。

## 五、测试：只测容易算错又难以察觉的核心逻辑

范围以 [开发规范的测试范围](DEVELOPMENT.md#测试范围) 为准。判断方法：**出错时用户在界面上一眼能看出来吗？** 能看出来就交给人工测试，看不出来（算错的数值、错误的数据转换、漏掉的校验）才写自动化测试。

## 六、代码放在哪：不许东一块西一块

- 写之前查 [目录职责](DEVELOPMENT.md#目录职责)，放进已有位置；同一功能的代码放在一起。
- 不新建 `utils`、`common`、`helpers`、`shared`、`misc` 之类的杂物目录，不建空目录或占位文件。
- 页面专用的组件和函数留在该页面文件或页面目录里，出现第二处真实复用时才提取到 `src/components/`。
- 不在源码目录放临时验证代码；临时文件放 `.local/` 或系统临时目录，不进仓库。
- 确实需要新目录或调整目录职责时，先说明理由征得同意，再同步更新 DEVELOPMENT。

## 七、验证与报告

- 提交前根目录执行 `npm run check`，结果如实报告。
- 界面改动在 `npm run dev` 下实际打开看过；没有看过的明确写“未在浏览器中验证”。
- 交付时如实区分：构建通过、我实测过的、需要用户人工试用的（附测试步骤）、未验证的。

## 八、交付前自查

执行 `git diff` 逐个文件看一遍，并检查：

- [ ] 每个改动的文件都是本任务需要的，没有无关的格式化、改名或重构。
- [ ] 没有新增空 `catch`、吞掉错误的 `catch`，没有 `any`、`@ts-ignore`、无理由的 `as`。
- [ ] 没有对类型已保证存在的值判空，没有对内部 props 的重复校验。
- [ ] 没有新增只用一次的抽象、包装组件或没人传的 props。
- [ ] 没有新建杂物目录或空目录。
- [ ] 能用 HeroUI 组件的地方没有手写同类控件；图标统一用 Lucide。
- [ ] 动效遵守减少动效设置；没有写死与主题冲突的颜色。
- [ ] 有意的简化都写了 `shortcut:` 注释。
- [ ] `npm run check` 通过。
